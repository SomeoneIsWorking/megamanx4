## Claim

our extracted SLUS_005.61 is sha1 213733031136d095ca275d6957695aa25011cfa5 (1,179,648 bytes) and matches the sozud/mmx4 decomp's declared byte-exact build target, so its symbol addresses are OUR addresses with no translation

## Evidence

MEASURED 2026-08-12. tools/extract_exe.py extracted SLUS_005.61 from the retail USA disc (resolved via $PSXPORT_X4_DISC; the path is machine-specific and deliberately not recorded here) using psxport's own discdump: 1,179,648 bytes, sha1 213733031136d095ca275d6957695aa25011cfa5, PS-X EXE with pc0=0x800DAE8C, text 0x80010000+0x11F800, sp=0x801FFFF0, d_size=b_size=0. INDEPENDENTLY, external/mmx4/check.us.txt (pin 1922fcd3) declares that SAME sha1 for its build/us/main.bin — the hash is read out of the submodule AT RUN TIME, never a hardcoded copy, so the check keeps tracking the reference it claims to check. DENOMINATORS from tools/verify_decomp_targets.py: 1 splat config discovered, 1 matched, 0 mismatched, 0 unchecked, 0 extract-failed; code images on the disc 1, covered 1, NOT covered none. NEGATIVE CONTROL: --selftest substitutes 40 zeros for the first target's expected hash and the run reports exactly one MISMATCH and exits 1 — the tool demonstrably CAN report the other answer. BLIND SPOT: a hash match says NOTHING about decomp COVERAGE (mmx4's own figure is an 18.5% upper bound, on the objdiff object-identity axis, not this port's SBS RAM-parity axis), and this does not build the decomp, so it does not check that mmx4 still PRODUCES that hash today.

## What would falsify it

a different disc dump (region/revision) yielding a different SLUS_005.61 sha1, or the external/mmx4 pin moving off 1922fcd3 to a commit whose check.us.txt states another hash — re-run python3 tools/verify_decomp_targets.py and python3 tools/extract_exe.py
